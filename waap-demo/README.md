# Avi WAAP for AI / MCP Demo Kit

This kit stands up a working "WAAP for AI" demonstration in which VMware Avi Load
Balancer acts as the single security enforcement point in front of unauthenticated
AI backends. It protects two Model Context Protocol (MCP) tool servers and an
OpenAI-compatible inference (LLM) service, and drives an interactive dashboard
that walks through mutual TLS, agent onboarding, least-privilege JWT
authorization, forged-token rejection, prompt-injection guardrails, a positive
security model, and session resilience under failover. Every stage is mapped to
both the OWASP API Security Top 10 (2023) and the OWASP MCP Top 10 (2025).

This README describes a manual deployment across three Ubuntu 22.04 LTS servers:
two backend servers that each run the MCP and LLM services, and one agent server
that runs Keycloak, the demo tools, and the dashboard. It assumes you already
have a working Avi Controller with a configured cloud, and that you will create
the Avi objects either with the included script or by hand.


## Architecture

```
                       +-------------------+
   Agent / Dashboard   |   Avi Load        |     Backend server A (Ubuntu 22.04)
   (Ubuntu 22.04)      |   Balancer        |       acme-mcp   : 8443 (TLS)
      api host  -----> |   enforcement     | --->  acme-llm   : 9443 (TLS)
                       |   point           |
   Keycloak (on agent) |                   |     Backend server B (Ubuntu 22.04)
      :8443            |   VS: MCP  (443)  | --->  acme-mcp   : 8443 (TLS)
                       |   VS: LLM  (443)  |       acme-llm   : 9443 (TLS)
                       +-------------------+
```

Two virtual services are created on Avi:

- MCP virtual service, fronting the two acme-mcp backends on 8443
- Inference virtual service, fronting the two acme-llm backends on 9443

Both require a client certificate (mutual TLS) and a valid Keycloak JWT. The
backends themselves have no authentication. Avi is the only thing protecting them.


## Server roles and naming

The examples below use these names and addresses. Substitute your own.

- Backend server A: acme-mcp-a, 10.15.148.90
- Backend server B: acme-mcp-b, 10.15.148.91
- Agent / dashboard / Keycloak host: acme-agent (api), reachable on your network
- MCP virtual service VIP: mcp.us-east.demo.lab
- Inference virtual service VIP: llm.us-east.demo.lab
- Keycloak: keycloak.demo.lab, port 8443
- Avi Controller: your existing controller

The MCP service listens on 8443. The inference (LLM) service listens on 9443.


## Prerequisites

On all three Ubuntu 22.04 LTS servers:

- Sudo access
- Network reachability to the Avi Controller and, for the backends, from the Avi
  Service Engines
- Node.js 18 or newer (the MCP and inference services are zero-dependency Node)
- open-vm-tools if running on vSphere (optional but recommended)

On the agent host additionally:

- Python 3.9 or newer
- A Java runtime (for Keycloak), or use the bundled JRE from the kit
- openssl and ssh client tools

On the Avi Controller:

- An existing cloud, Service Engine group, and network such that a new virtual
  service can receive the VIPs above
- Admin credentials

You also need the demo PKI (a CA, a server certificate, and an agent client
certificate) and a Keycloak realm with three tier clients. Both are generated by
the kit, described below.


## What you will build, in order

1. Generate the demo PKI (CA, server cert, agent client cert)
2. Set up the two backend servers (MCP and LLM services)
3. Set up the agent server (Keycloak, tools, dashboard)
4. Configure Keycloak (realm, three tier clients, mcp_tier and audience mappers)
5. Configure Avi (certificates, PKI profile, JWT, SSO policy, WAF, PSM, pools,
   two virtual services)
6. Verify end to end and run the demo


## Step 1. Generate the PKI (on the agent host)

The kit generates a self-signed CA, a server certificate with subject
alternative names, and an agent client certificate for mutual TLS. No external CA
is contacted.

```
cd avi-waap-mcp-demo-kit
bash scripts/gen-certs.sh
```

This writes to config/certs/:

- ca.crt, ca.key            the demo root CA
- server.crt, server.key    server cert (SANs cover the VIP and service names)
- client.crt, client.key    the agent client certificate for mutual TLS

Edit config/config.env first if you want to change the certificate subject names
or the domain. The client certificate is what the agent presents to Avi on every
request once mutual TLS is in Require mode, so keep client.crt and client.key
safe and readable by the services that use them.


## Step 2. Set up the two backend servers

Do this on BOTH acme-mcp-a and acme-mcp-b. The steps are identical except for the
node name.

### 2a. Install Node.js

If Node 18+ is not already present:

```
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt-get install -y nodejs
node --version
```

In a true airgap, copy the vendored Node runtime from the kit instead and place
it on the path.

### 2b. Create the service user and directories

```
sudo useradd --system --home /opt/acme-ai --shell /usr/sbin/nologin acme
sudo mkdir -p /opt/acme-ai/certs
```

### 2c. Copy the service code and certificates

From the kit, copy the two service files and the server certificate material to
each backend:

```
# from your workstation or the agent host, for each backend IP:
scp backend/mcp-server.js backend/inference-stub.js ubuntu@10.15.148.90:/tmp/
scp config/certs/server.crt config/certs/server.key config/certs/ca.crt ubuntu@10.15.148.90:/tmp/

# then on the backend:
sudo cp /tmp/mcp-server.js /tmp/inference-stub.js /opt/acme-ai/
sudo cp /tmp/server.crt /tmp/server.key /tmp/ca.crt /opt/acme-ai/certs/
sudo chown -R acme:acme /opt/acme-ai
sudo chmod 640 /opt/acme-ai/certs/server.key
```

### 2d. Create the systemd units

Create /etc/systemd/system/acme-mcp.service (set NODE_NAME per host, for example
mcp-a-01a on server A and mcp-a-01b on server B):

```
[Unit]
Description=ACME MCP server
After=network-online.target
Wants=network-online.target

[Service]
User=acme
WorkingDirectory=/opt/acme-ai
Environment=NODE_NAME=mcp-a-01a
Environment=MCP_PORT=8443
Environment=TLS_CERT=/opt/acme-ai/certs/server.crt
Environment=TLS_KEY=/opt/acme-ai/certs/server.key
Environment=RESUME_SESSIONS=1
ExecStart=/usr/bin/node /opt/acme-ai/mcp-server.js
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
```

Create /etc/systemd/system/acme-llm.service:

```
[Unit]
Description=ACME inference stub
After=network-online.target
Wants=network-online.target

[Service]
User=acme
WorkingDirectory=/opt/acme-ai
Environment=LLM_NODE_NAME=mcp-a-01a
Environment=LLM_PORT=9443
Environment=LLM_TLS_CERT=/opt/acme-ai/certs/server.crt
Environment=LLM_TLS_KEY=/opt/acme-ai/certs/server.key
ExecStart=/usr/bin/node /opt/acme-ai/inference-stub.js
Restart=always
RestartSec=2

[Install]
WantedBy=multi-user.target
```

Note on the inference service: it responds to /v1/chat/completions with a single
buffered (non-streaming) response by default. This is deliberate. A streamed
response races with the WAF block at Avi and produces intermittent connection
resets instead of clean 403s. If you specifically want to demonstrate token
streaming, set Environment=FORCE_STREAM=1 in the acme-llm unit.

### 2e. Enable and start both services

```
sudo systemctl daemon-reload
sudo systemctl enable --now acme-mcp.service acme-llm.service
systemctl status acme-mcp acme-llm --no-pager
```

Confirm both are listening:

```
sudo ss -ltnp | grep -E '8443|9443'
```

You should see node listening on 8443 (MCP) and 9443 (LLM). Repeat all of Step 2
on the second backend, changing NODE_NAME and LLM_NODE_NAME to identify it.

### 2f. Install the agent failover key (for the session-resilience stage)

The failover stage stops the MCP service on one node over SSH. Generate the key
on the agent host (Step 3) and install the public key here, with a scoped
sudoers rule so the agent can only control the MCP service:

```
# on each backend, after you have the agent public key:
cat waap-demo.pub >> /home/ubuntu/.ssh/authorized_keys
sudo tee /etc/sudoers.d/waap-failover >/dev/null <<'EOF'
ubuntu ALL=(root) NOPASSWD: /usr/bin/systemctl stop acme-mcp, /usr/bin/systemctl start acme-mcp, /usr/bin/systemctl restart acme-mcp
EOF
sudo chmod 440 /etc/sudoers.d/waap-failover
```


## Step 3. Set up the agent server

This host runs Keycloak, the demo tools (agent.py and attack.py), and the
dashboard.

### 3a. Install runtimes

```
sudo apt-get update
sudo apt-get install -y python3 python3-venv openssl openjdk-17-jre unzip
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt-get install -y nodejs
```

### 3b. Generate the agent SSH keypair (for failover)

```
cd avi-waap-mcp-demo-kit
bash scripts/gen-ssh.sh
```

This writes config/ssh/waap-demo (private) and waap-demo.pub (public). Install
the public key on both backends as shown in Step 2f.

### 3c. Install Keycloak

Download Keycloak (or use the bundled zip from the kit vendor directory) and
install it under /opt/keycloak. Point it at the demo server certificate for TLS:

```
sudo mkdir -p /opt/keycloak/conf
sudo cp config/certs/server.crt /opt/keycloak/conf/server.crt.pem
sudo cp config/certs/server.key /opt/keycloak/conf/server.key.pem
```

Create /etc/systemd/system/keycloak.service, setting the admin credentials and
the HTTPS port to 8443:

```
[Unit]
Description=Keycloak
After=network-online.target
Wants=network-online.target

[Service]
Environment=KC_BOOTSTRAP_ADMIN_USERNAME=admin
Environment=KC_BOOTSTRAP_ADMIN_PASSWORD=CHANGE_ME
WorkingDirectory=/opt/keycloak
ExecStart=/opt/keycloak/bin/kc.sh start-dev --https-port=8443 --https-certificate-file=/opt/keycloak/conf/server.crt.pem --https-certificate-key-file=/opt/keycloak/conf/server.key.pem --hostname-strict=false
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

Start it:

```
sudo systemctl daemon-reload
sudo systemctl enable --now keycloak.service
```

Make sure the name you will use for Keycloak (for example keycloak.demo.lab)
resolves to this host, since the token issuer and the Avi JWT profile must agree
on that exact name and port.

### 3d. Install the demo tools and dashboard

```
sudo mkdir -p /opt/waap-demo/tools /opt/waap-demo/dashboard /opt/waap-demo/certs /opt/waap-demo/.ssh
sudo cp agent/tools/agent.py agent/tools/attack.py /opt/waap-demo/tools/
sudo cp agent/dashboard/* /opt/waap-demo/dashboard/
sudo cp config/certs/client.crt config/certs/client.key config/certs/ca.crt config/certs/server.crt config/certs/server.key /opt/waap-demo/certs/
sudo cp config/ssh/waap-demo /opt/waap-demo/.ssh/waap-demo
sudo chmod 600 /opt/waap-demo/.ssh/waap-demo /opt/waap-demo/certs/client.key /opt/waap-demo/certs/server.key

python3 -m venv /opt/waap-demo/venv
/opt/waap-demo/venv/bin/pip install fastapi "uvicorn[standard]" requests PyJWT cryptography python-multipart
```

In an airgap, install the Python packages from the vendored wheels with
--no-index --find-links instead of from the internet.

### 3e. Create the dashboard service

Create /etc/systemd/system/waap-demo.service. The environment here is important:
it must include the client certificate for mutual TLS and both virtual service
URLs. This is one of the most common places a deployment goes wrong. If the
client certificate is not in the service environment, every call fails at the
mutual TLS handshake once Avi is in Require mode.

```
[Unit]
Description=WAAP demo dashboard
After=network-online.target keycloak.service
Wants=network-online.target

[Service]
WorkingDirectory=/opt/waap-demo/dashboard
Environment=DEMO_TOOLS_DIR=/opt/waap-demo/tools
Environment=AVI_MCP=https://mcp.us-east.demo.lab
Environment=AVI_LLM=https://llm.us-east.demo.lab
Environment=KC=https://keycloak.demo.lab:8443
Environment=KC_REALM=acme-ai
Environment=SECRET_CATALOG=CHANGE_ME
Environment=SECRET_OPS=CHANGE_ME
Environment=SECRET_FINANCE=CHANGE_ME
Environment=CID_CATALOG=agent-catalog
Environment=CID_OPS=agent-ops
Environment=CID_FINANCE=agent-finance
Environment=CLIENT_CERT=/opt/waap-demo/certs/client.crt
Environment=CLIENT_KEY=/opt/waap-demo/certs/client.key
Environment=MCP_A_IP=10.15.148.90
Environment=MCP_B_IP=10.15.148.91
Environment=FAILOVER_WAIT=8
Environment=DEMO_TLS_CERT=/opt/waap-demo/certs/server.crt
Environment=DEMO_TLS_KEY=/opt/waap-demo/certs/server.key
ExecStart=/opt/waap-demo/venv/bin/python /opt/waap-demo/dashboard/waap_demo_server.py
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

Start it:

```
sudo systemctl daemon-reload
sudo systemctl enable --now waap-demo.service
systemctl status waap-demo --no-pager
```


## Step 4. Configure Keycloak

Create the realm, the three tier clients, the mcp_tier claim mapper, and the
audience mapper. The audience mapper is essential: the token aud claim must match
the Audience field you set on the Avi virtual services, or every token is
rejected with a 401.

Run the included script on the agent host, with AUDIENCE_VALUE set to the value
you will also put in the Avi Audience field:

```
export KC_HOME=/opt/keycloak
export KC_ADMIN_USER=admin KC_ADMIN_PASSWORD=CHANGE_ME
export KC_REALM=acme-ai KC_HTTPS_PORT=8443
export KC_CID_CATALOG=agent-catalog KC_SECRET_CATALOG=CHANGE_ME
export KC_CID_OPS=agent-ops KC_SECRET_OPS=CHANGE_ME
export KC_CID_FINANCE=agent-finance KC_SECRET_FINANCE=CHANGE_ME
export AUDIENCE_VALUE=https://mcp.demo.lab
bash keycloak/configure-keycloak.sh
```

This creates:

- Realm acme-ai with a 600 second access token lifespan
- Three confidential clients with service accounts and direct access grants
- A hardcoded-claim mapper stamping mcp_tier (catalog, ops, or finance)
- An audience mapper stamping aud equal to AUDIENCE_VALUE

Verify a token mints and carries the right claims:

```
curl -sk -d "grant_type=client_credentials" \
  -d "client_id=agent-catalog" -d "client_secret=CHANGE_ME" \
  https://keycloak.demo.lab:8443/realms/acme-ai/protocol/openid-connect/token \
  | python3 -c "import sys,json,base64; t=json.load(sys.stdin)['access_token']; p=t.split('.')[1]; p+='='*(-len(p)%4); print(json.dumps(json.loads(base64.urlsafe_b64decode(p)),indent=2))"
```

Confirm the decoded token shows iss (your Keycloak issuer, including the port),
aud (equal to AUDIENCE_VALUE), and mcp_tier (catalog).


## Step 5. Configure Avi

You can run the included script or build the objects by hand. The script talks
only to your controller over its REST API.

```
# on a host that can reach the controller, with the requests package available:
AVI_CONTROLLER=... AVI_USER=admin AVI_PASSWORD=... AVI_TENANT=admin \
AVI_CLOUD="Default-Cloud" AVI_SE_GROUP="Default-Group" \
AVI_VS_NETWORK="10.15.148.0/24" AVI_VIP="10.15.199.1" AVI_VERSION="32.1.1" \
... (see config/config.env for the full list) \
python3 avi/configure-avi.py
```

Whichever way you build them, these are the objects and the settings that matter.
Several of these were learned the hard way, so pay attention to the notes.

Certificates and PKI:

- Import the CA (ca.crt) as a CA certificate object
- Import the server certificate and key as a virtual service certificate
- Create a PKI profile that trusts the demo CA. This is what validates the agent
  client certificate for mutual TLS

JWT and SSO:

- JWT server profile: issuer must exactly match the token iss, including the port
  (for example https://keycloak.demo.lab:8443/realms/acme-ai). Point it at the
  Keycloak JWKS endpoint
- Auth profile of type JWT referencing the JWT server profile
- SSO policy referencing the auth profile, with authorization rules below

Authorization rules (this is the part that most often needs care):

- Use the JSON Web Tokens (JWT) match type, not a generic attribute match. Set
  Token Name to the JWT server profile, Claim Name to mcp_tier, Type to String,
  Criteria to Equals, and the value to the tier
- allow-catalog: path begins with /mcp/catalog and mcp_tier equals catalog
- allow-ops: path begins with /mcp/ops and mcp_tier equals ops
- allow-finance: path begins with /mcp/finance and mcp_tier equals finance
- allow-inference: path begins with /v1/ and mcp_tier is in catalog, ops, finance
- deny-all (last): path begins with / and action is an HTTP 403 local response.
  Do not use Close Connection here. Close Connection drops the socket with no
  response, which the demo tools see as a connection error rather than a clean
  blocked result

WAF:

- WAF profile with request and response body inspection enabled, JSON content
  type mapped to the JSON parser, and a nonzero maximum backend response size
- WAF policy in Enforcement mode with a Pre-CRS group named AI-GUARDRAILS
  containing the prompt-injection, sensitive-action, hidden-instruction, and
  template/SSTI rules (ids 1000001 to 1000004)
- A Positive Security Model group named MCP-ToolsCall-PSM with a location that
  matches path begins-with /mcp/, and an argument rule arg-query on
  params.arguments.query with the pattern ^[\w\s.-]{1,40}$. The short max length
  is what rejects sentence-shaped prompt injections while allowing real searches

Application profiles (important distinction):

- The MCP virtual service uses the secure MCP application profile, which handles
  the MCP session and streaming transport
- The inference virtual service must use a standard secure L7 HTTP profile, NOT
  the MCP profile. The MCP profile runs session and persistence logic that does
  not apply to the /v1 path and causes inconsistent behavior there

Health monitor and pools:

- A health monitor that checks the backend on its port
- MCP pool (AI-MCP-L7-Vs-Pool): the two backends on 8443, with an SSL profile
  (System-Standard) and SSL enabled toward the servers. The backends serve TLS,
  so the pool must speak TLS to them. Without this the connection is closed after
  auth passes
- Inference pool: the two backends on 9443, also with an SSL profile

Virtual services:

- MCP virtual service on the MCP VIP, port 443 with SSL, binding the server
  certificate, the PKI profile (for mutual TLS), the SSO policy, the WAF policy,
  the MCP application profile, and the MCP pool
- Inference virtual service on the inference VIP, port 443 with SSL, binding the
  same server certificate, PKI profile, SSO policy, and WAF policy, the standard
  L7 application profile, and the inference pool

Mutual TLS mode:

- Set client certificate validation to Require on both virtual services. In
  Require mode every request must present the agent client certificate, which is
  why the dashboard service environment includes CLIENT_CERT and CLIENT_KEY

Audience:

- On both virtual services, set the JWT Audience field to the exact value you
  used for AUDIENCE_VALUE in Keycloak (for example https://mcp.demo.lab). A
  mismatch here rejects every token with a 401


## Step 6. Verify end to end

From the agent host, mint a token and call the MCP virtual service with both the
client certificate and the token:

```
TOKEN=$(curl -sk -d "grant_type=client_credentials" \
  -d "client_id=agent-catalog" -d "client_secret=CHANGE_ME" \
  https://keycloak.demo.lab:8443/realms/acme-ai/protocol/openid-connect/token \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

curl -sk --cert /opt/waap-demo/certs/client.crt --key /opt/waap-demo/certs/client.key \
  -H "Authorization: Bearer $TOKEN" -H "content-type: application/json" \
  -X POST https://mcp.us-east.demo.lab/mcp/catalog \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"inventory.lookup","arguments":{"sku":"SKU-4410"}}}'
```

Expected results as you build up:

- No client certificate: the TLS handshake is rejected (mutual TLS working)
- Client certificate, no token: a clean 401 from Avi (JWT enforcement working)
- Client certificate and a valid catalog token to /mcp/catalog: a 200 result
- Client certificate and a catalog token to /mcp/finance: a 403 (tier
  authorization working)

Then open the dashboard at https://AGENT_HOST:8700/ and run the stages.

## Troubleshooting, from real deployment experience

Connection closed with no response, or the tool reports a connection error:

- Almost always mutual TLS. In Require mode the caller must present the agent
  client certificate. Confirm CLIENT_CERT and CLIENT_KEY are set in the
  dashboard service environment and readable by the service user. Test by hand
  with curl --cert and --key

Clean 401 with a valid token:

- Audience or issuer mismatch. Decode the token and confirm aud equals the Avi
  Audience field, and iss (including the port) equals the JWT server profile
  issuer

Empty reply or 503 after auth passes:

- The pool is speaking plaintext to a TLS backend. Attach an SSL profile to the
  pool and enable SSL toward the servers. Also confirm the pool port is 8443 for
  MCP and 9443 for inference, not swapped

Requests fall through to the deny rule and the connection closes:

- The lane authorization rules are not matching. Use the JSON Web Tokens match
  type with Claim Name mcp_tier, and make sure deny-all is the last rule. Change
  the deny action from Close Connection to an HTTP 403 local response so denials
  are visible

Inference (LLM) path gives inconsistent 403, 503, and connection errors:

- The inference virtual service is using the MCP application profile. Change it
  to a standard secure L7 HTTP profile. Confirm the inference service returns a
  buffered (non-streaming) response, which is the default

Template or SSTI payload is allowed on the MCP path:

- Add the template rule (id 1000004) to the AI-GUARDRAILS Pre-CRS group, and
  confirm the PSM arg-query pattern is ^[\w\s.-]{1,40}$ with the short max length


## Security notes

This kit is for demonstration in a controlled lab. It uses a self-signed CA,
generated client secrets, and permissive TLS verification against the lab
controller. Do not reuse these certificates, keys, or credentials outside the
demo. The scoped sudoers rule on the backends permits only start, stop, and
restart of the MCP service by the agent, nothing else.
